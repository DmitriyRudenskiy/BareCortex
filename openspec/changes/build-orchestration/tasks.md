# Tasks: build-orchestration

Scope note: nothing here needs the **target** machine. The only task touching that host writes a checklist and records that running it belongs to `target-hardware-bring-up`.

Task classification (0.4): a task with **no marker is `write`** — it is finished by a file in this repo. A task marked **`(run)`** is finished only by an execution whose output is recorded, and is blocked until a host exists. Four tasks are `run`: **4.3, 4.5, 5.3, 6.5**. Nothing else in this file needs a machine, including the two that read as if they do: 4.4's retention limit is proven against snapshot files in a directory, and 6.6's synthetic fragment is proven against a kernel-config fixture — both recorded as `write`, and 6.6 says in its own words that a passing proof there means nothing about a real machine.

- [x] 1.3 Decide the checkpoint medium (OQ2) against the build host's filesystem, and record that the tar path remains the fallback. **External qcow2 snapshots**, taken by `scripts/build/vm-host.sh snapshot <phase>`: the current image is renamed into `sn/<phase>-<gen>.qcow2` and becomes an immutable backing file, and a fresh child is created on top with `qemu-img create -b`, so freezing a phase costs a rename and a create and rollback is choosing a different parent. It is chosen *against the build host's filesystem* in the literal sense that 0.1 names the host: the LFS disk is a qcow2 inside the substrate's `$HOME` on ext4/NVMe with 119 G free, so the medium is a file operation the substrate already does for the guest's own disk, and the guest never has to mount anything to be checkpointed. **Measured:** the first checkpoint, `chroot-layout-0`, is 13 MB allocated against a 599 MB `$LFS` — an external snapshot stores what changed since its parent, which is what keeps a checkpoint after every phase affordable. **The tar path remains the fallback and says so in one place:** `snapshot` and `rollback` are the only verbs in the repo that know what a checkpoint is made of, so a build root that is a physical partition or a filesystem without qcow2 is a rewrite of those two functions, not a change to `phases.toml`, `build.py`, or any phase record — the record stores the tag, never the medium. One failure mode is already recorded in the script: the first implementation `mv`'d the child over an existing parent and made the disk its own backing file, and `qemu-img` recursed through the chain until it ran out of descriptors; generations per tag are why a re-checkpointed phase is safe

- [x] 2.4 Record the trust boundary of 2.2 in one paragraph: checksums verified, signing keys not, and what class of failure that does and does not defend against. **Verified, every build:** all 93 files `base.lock` names are compared against the MD5 in the book's own download table, by the fetch step, before anything is unpacked, and a mismatch — or a file that is not there — names the file and fails the phase. **Not verified:** no signature, no key, no publisher fingerprint is checked for anything; no SHA-256 is computed or compared; nothing is fetched from a second mirror to see whether it agrees. So the class of failure this defends against is *damage and drift*: a truncated or resumed-wrong download, a mirror serving a stale or partially-uploaded tarball, a bit-rotted file reused from `$LFS/sources` months later, a package swapped for a different version than the pin says. The class it does **not** defend against is *an attacker who controls what arrives*: the checksums travel over the same HTTPS channel as the pages, so the trust root is the transport to linuxfromscratch.org and to the download sites, not the hash — and MD5 is not collision-resistant, so a deliberately crafted pair of archives is outside what this stops. The one entry that is `[[unattributed-download]]` (`Libpipeline 1.5.8`, in the book's table and on no page of this edition) sits at the weak end even inside this boundary: its checksum is the book's, and its provenance is the book's silence. Changing the boundary means changing what is pinned — SHA-256 and per-upstream key checks where upstream publishes a key — and that is a pin-bump decision with a reviewable diff (2.3), not a switch the fetch step can flip, because what the book publishes today is MD5

## 4. State record and checkpoints

- [x] 4.1 Define the state record: last passed phase, artifacts, timestamp, `base.lock` identity. The record is `build-evidence/<phase>/record.json`, written by one function (`write_record`) so no phase can omit a field: `phase`, `started`/`finished`, the `context` the pages ran in, how many pages ran, `results` naming every per-page log (the artifacts), `criteria` with each check's command, exit code and output, `passed` computed from those and never asserted, the phase's `entry`/`exit_criteria` text copied from `phases.toml` so the record says what it was judged against, and the checkpoint tag. **Last passed phase** is `build.py status`, which reads every record and prints phase, passed/FAILED, page count, checkpoint and finish time — so resume reads the disk, not a memory. **`base.lock` identity was missing and went in with this task:** every record now carries `base_lock`, the SHA-256 of `base.lock`'s bytes, and `book`, the edition URL the pages were read from, because a passing record that does not name its inputs cannot be evidence about any of them
- [x] 4.2 Write the record only after exit criteria pass, and verify a crash mid-phase leaves the previous record intact. `write_record` is called once per phase, after every page returned and after `verify` ran, so a phase that dies halfway has written nothing about itself. It was also writing in place, which is not the same claim: a death during the write truncates the record of the run that *passed*. Now it writes `record.json.tmp` and `os.replace`s it, so the file is either the old record or the new one. Verified by `scripts/build/test_build.py`: a half-written `record.json.tmp` sits next to a `record.json` that still parses with `passed: true`, and a finished write leaves no temp file behind
- [x] 4.3 **(run)** Implement resume-at-next-phase and prove it with a deliberately failed phase. `build.py resume` reads every `record.json`, takes `next_phase()` — the first phase in `phases.toml` order with no passed record, so **a failed phase keeps its name** and a later phase passing does not skip past it (`check_resume_starts_at_the_failed_phase`) — rolls the LFS disk back to the previous phase's checkpoint — **unconditionally**, because a phase's writes are only worth keeping once it has passed, and a backing-chain check cannot tell "the disk is the checkpoint" from "the disk is the checkpoint covered in the failed phase's own writes" — then re-runs `sources` if the rollback took a tarball with it (1.3 freezes the whole disk, `$LFS/sources` included, while `sources` goes on recording passed), and runs the phase. Two things the first real run corrected: the checkpoint's tag is the **phase name**, not the record's `checkpoint` field, which holds the `phases.toml` policy word `after` and sent the first version looking for `sn/after-0.qcow2`; and the sources check has to run **after** the rollback, not before, because the dirty disk still had the tarballs the checkpoint never contained. The rollback is the part a person forgets, and this change got to prove it with two real failures rather than a synthetic one: `temp-tools` failed twice on the same disk (once on a Ncurses C++ binding with no libstdc++ to link, once on `ln -sv libncurses.so` meeting the symlink its own earlier attempt left behind), and each time the honest resume was `vm-host.sh rollback cross-toolchain-0` — not `run temp-tools` again, which would have built chapter 6's remaining pages on a half-installed `$LFS`. `vm-host.sh rollback` takes a generation (`cross-toolchain-0`, not `cross-toolchain`) because 1.3's per-tag generations mean a tag can name several checkpoints, and resume resolves the newest itself. The second failure is the one that says why resume must roll back at all: a chapter 6 page is not idempotent — `ln -sv` without `-f` fails on the file a previous attempt installed — so re-running a failed phase in place is a different build, not a retry of it.
- [x] 4.4 Implement checkpoints with a bounded retention count, and verify the retention limit actually deletes — **implemented as reachability, because a count is the wrong unit for a qcow2 chain.** `vm.sh prune [--do]` asks `qemu-img info -U --backing-chain lfs.qcow2` which checkpoint files the working image is built on and deletes every file in `sn/` that is not one of them; `snapshot` runs it after every checkpoint. A checkpoint is a link in a chain — `temp-system-1` is backed by `enter-chroot-0`, which is backed by `temp-tools-0` — so "keep the newest two" would delete a live image's parent and corrupt the disk, while the files that are genuinely dead weight are the branches a rollback abandoned, and reachability names exactly those. The bound is therefore one chain (eleven phases, one delta each) plus nothing else, which is what the disk actually needs: after seven phases `sn/` held 25 G of which 1,2 G was off-chain. **Deletion is verified, with the chain as the control:** two empty `sn/zzz-prune-test-*.qcow2` files plus the real off-chain `temp-system-0` were pruned by `prune --do` ("pruned 3 checkpoint(s)"), the six on-chain files survived, and `qemu-img info` still opened the working image and named its parent. **Two bugs the dry run caught before the delete could:** the keep-list is newline-separated while the `case` pattern looked for space-delimited names, so *nothing* matched and the first real run — the checkpoint at the end of chapter 8, with the build live — would have deleted all seven checkpoints including the parent qemu had open; and `qemu-img info` without `-U` cannot read a running image, so the guard that refuses to prune when the chain cannot be read fired on the very first attempt. Both are why `prune` prints what it would delete by default and deletes only when told.
- [x] 4.5 **(run)** Verify a checkpoint restores a build tree to the state before the last passed phase. Run on the real disk, twice, against `sn/cross-toolchain-0.qcow2` (8.8 G, the checkpoint `cross-toolchain` recorded): after `vm.sh rollback cross-toolchain-0` the guest came up in 2 s and `$LFS` — which had held sixteen installed temporary tools, a `libncurses.so` symlink and a half-built GCC tree — answered `ls /mnt/lfs/usr/lib/libncurses*: No such file or directory`, `/mnt/lfs/tools/bin` held the 28 files of the cross toolchain and nothing else, and `/mnt/lfs/sources` held 92 entries instead of the 94 the failed run had left. **The state restored is the state before the last passed phase, and it is the whole disk, sources included** — which is the consequence 4.3 had to design around: the two tarballs fetched after the checkpoint were gone with it, while `sources` still recorded `passed`, so resume needed `guard_present()` to notice the disk no longer matched the record instead of failing two pages later with `tar: ncurses-6.6.tar.gz: Cannot open`. Rollback is choosing a different parent (`rm lfs.qcow2; qemu-img create -b sn/<tag>-<gen>.qcow2`), so it costs one create and cannot half-restore: either the new child exists and every write after the checkpoint is gone, or the old child is still there.
- [x] 4.6 Lock the build root for the duration of a run: a second invocation fails naming the holding process, and a lock whose owner is gone is reported as stale with the action that clears it. `.build-lock` holds the owner's pid, what it is running and when it started, and is created with `O_CREAT|O_EXCL` so two simultaneous starters cannot both believe they won; `run` and `fetch` take it before they touch anything and release it in a `finally`. **Both failure modes demonstrated with two real processes, not asserted:** while a holder was alive, `build.py run sources` printed `build root is locked by pid 39083 running /Library/…/Python -c …` — that run owns $LFS and the snapshot chain — and exited 1 without reaching the guest; with the file rewritten to a pid nobody owns it printed `stale lock: /Users/user/BareCortex/.build-lock names pid 999999, which is not running — the last build died mid-phase. Nothing owns $LFS now; clear it with: rm /Users/user/BareCortex/.build-lock`, again exit 1. It refuses rather than clearing a stale lock by itself, because “the last build died mid-phase” is exactly the moment a human should look at the phase record before another run starts writing over it. A live pid belonging to another user counts as alive (`PermissionError` is not “gone”), and `test_build.py::check_build_root_lock` covers held, released and stale

## 5. Fetch, verify, and deny the network

- [x] 5.1 Implement the fetch step over `base.lock`, with checksum verification failing the build and naming the file. `build.py fetch` walks all 93 entries (88 packages, 5 patches), downloads each to `<name>.part` and renames only on success, clears any `.part` left by an interrupted run before resuming, then compares `md5sum` against the MD5 the book published — the comparison is the `sources` phase's exit criterion, so a mismatch fails the phase and names the file in `criteria[].out`. **A bug in the failure path, found while testing it:** the parser unpacked four fields from every `@@MD5` line, and a file that never downloaded prints three (`md5sum` had nothing to hash), so the fetch crashed with `ValueError` instead of failing the build. `mismatches()` now handles all four shapes — match, mismatch, absent file, `@@FETCH-FAIL` — deduplicates and sorts them, and `test_build.py::check_mismatches` asserts each one, including that a matching checksum is not a failure
- [x] 5.2 Fail any build step that references a source absent from `base.lock`, before downloading anything. `guard_sources(pages)` runs at the top of `run_phase`, before any page runs: it takes every command block of every page the phase would run, extracts the file names they mention, adds every `archive` value in `build-overrides.toml`, and fails the phase naming `page: file` for anything outside `base.lock`'s 93 names — the record is written with `unsourced` and `checkpoint: none`, and nothing was fetched or unpacked. The override path is the one that could name anything, since `archive_for()` derives the archive *from* the lock and cannot invent one. Run over all eleven phases (140 pages): **zero unsourced references today**, which is the state, not the guard's purpose. Two regex lies surfaced while testing it: `gzip`, `gunzip` and `bunzip` matched `zip`, and a lazy token matched `2-1.0.8-install_docs-1.patch` out of `bzip2-1.0.8-install_docs-1.patch`; both fixed by requiring a token boundary and a digit, and the test asserts the real bzip2 `patch -Np1 -i ../…` line yields exactly one name, plus that a fabricated `tar -xvf linux-99.9.9.tar.xz` and a fabricated override archive each stop their phase
- [x] 5.3 **(run)** Run a full phase with the network denied and record what it needed, so the claim rests on a run rather than an intention — **seven phases have run that way, and the answer is: nothing.** Every command of every page goes through `wrap(..., net=False)` → `unshare -n`, so `host-prep`, `sources` (the one phase that asks for network, to fetch), `chroot-layout`, `cross-toolchain`, `temp-tools`, `enter-chroot` and `temp-system` — **41 pages and 150 command blocks**, including every chapter 5 and 6 compile — ran with no routes and no interfaces, and no page failed for want of a download. **The probe, with a control, measured 2026-11-11:** a TCP connect to the guest's own default gateway prints `gw=10.0.2.2 REACHED` outside the namespace and `gw= DENIED` inside it — the namespace has no route to learn, which is the property being claimed. The first probe was thrown out because both halves printed DENIED: it used `curl` against the substrate's LAN address, which the guest's user-mode network cannot answer either way, so it proved nothing about the namespace. **What the claim rests on is now in the record**, not only in the code: every phase record carries `net: "denied (unshare -n: ...)"`, so a phase that ever runs with network cannot be confused with one that did not.
- [x] 5.4 Record the cache location and its invalidation rule. Two caches, both recorded where the code reads them. **Sources: `$LFS/sources` itself** — a file that exists with the published checksum is never requested again, an interrupted fetch's `.part` files are deleted before anything resumes, and there is no second copy to be stale; invalidation is deleting the file, and a checksum mismatch is not an invalidation but a stopped build. **Book pages: `.book-cache/`** — keyed by page path, which turned out to be edition-blind: `chapter05/binutils-pass1.html` exists in every edition of the book, so pointing `book.BASE` at a new pin would have silently mixed two editions' commands into one build. The cache now records the base URL it was filled from and any build against a different base fails, naming `rm -rf .book-cache` as the action. The rule in one line: **one cache per pinned edition, and moving to a new edition is a deliberate deletion, not a silent miss**
- [x] 5.5 Implement the network **denial mechanism** (`unshare -n` or the host's equivalent) and record its failure mode, so "phases run without network" is a property of the phase and not a story about a cable. 5.3 tests what this task builds; neither replaces the other. `wrap()` prefixes every command of every context with `sudo unshare -n` — a fresh network namespace, empty by construction — and the namespace is created as root before the command is dropped to whoever the context runs as, so the denial does not depend on the build user being unprivileged. `fetch()` is the single caller passing `net=True`, because fetching is the one step the design gives network to. **Verified in the guest 2026-11-11:** `host-root` runs as root and `host-lfs` runs as `lfs`, both inside the namespace, both showing `ip -o link` with one interface — `lo: <LOOPBACK> … state DOWN` — and no other; `wget https://example.com` inside exits **4** ("Network is unreachable": no interface is up, so there is no route), while `echo $((6*7))` still prints 42 and the same `wget` with `net=True` prints `NET OK`. So the failure mode of a phase that wants the network is a nonzero exit at the connect, in that phase's log, naming the command — not a silent download. **Also found, and not caused by this:** `chroot-root` currently dies with `chroot: failed to run command '/usr/bin/env': No such file or directory`, identically with and without `unshare -n`, because `$LFS/usr/bin` is empty at chapter 5 — a fact about where the build has reached, recorded here so the next reader does not blame the namespace for it
