# Proposal: image-minimisation

## Why

`README.md:6` prints "No bloat." Nothing in the repository decides what the image
contains: the image is whatever the pinned book builds, which today is all 94
entries of `base.lock`, each present because a chapter 8 page builds it and not
because BareCortex chose to ship it. Vim, Man-DB, Man-pages, Groff, Tcl, Expect,
DejaGNU, the three `* Documentation` packages and the toolchain are in the image
of a headless five-GPU training node for the same reason — the book builds them.

Removal is not an operation anyone can perform today. There is no package
manager, by decision (`build-orchestration` D1, following the book's own §8.2,
which declines to recommend one), so nothing records which files a package
installed, and therefore no way to answer the only question that matters before
deleting anything: does anything else in this image load a library that package
provides? A "No bloat" badge over an undecided package set is this project's
founding defect class — an assertion with no command behind it. This change makes
the claim a decision, the decision a record, and the record a command's output.

## What Changes

- **Every `base.lock` entry gets a verdict**: `ships` (in the image), `build-only`
  (installed, consumed by a later build step, removed before the image is
  frozen), or `absent` (never installed). A package with no verdict is a build
  failure, so the set of decisions is the whole package set and not a list of
  grievances.
- **The verdicts are a hand-authored file, `image-trim.toml`, keyed by the names
  in `base.lock`** — never a field inside it. `base.lock` is regenerated by
  `derive-base-lock.py`, which prints "do not edit by hand" in its own header, and
  a hand-authored section inside a derived file is that derivation's collateral
  damage; `class-map.toml` exists for exactly this reason and is the precedent.
  A check fails any row naming a package `base.lock` does not have, which is what
  keeps this a delta over the one package truth instead of a second list.
- **File ownership becomes a recorded artifact**, by the technique the pinned
  book itself documents — §8.2.2.4 "Timestamp Based": stamp a file, install one
  package, `find` what is newer. It needs no package that `base.lock` lacks, and
  the book states its two drawbacks, which are recorded with it. The
  orchestrator's existing exclusivity lock (`build-orchestration` D11) is what
  satisfies the "one package at a time" condition.
- **Dependency edges come from the binaries, not from prose.** The cited `ldd(1)`
  page establishes two things that shape the scan: `ldd` takes *files* and prints
  the libraries each requires — it is not a package query — and its BUGS section
  says pointing it at a binary it cannot interpret makes it *execute* that binary
  with `argc = 0`. So the whole-image edge scan reads ELF headers without
  executing anything (`objdump -p` / `readelf -d`), and `ldd` is used where its
  specific property is needed — resolving what the loader actually loads for a
  named program — run inside the image against the image's own loader, never on
  the build host.
- **A dependency graph, queryable, built by graphify** from those edges. Every
  edge is `EXTRACTED` from scan output; the LLM extractor is not used, because an
  inferred edge in a removal decision is a guess about why the node will not
  boot. The removal question becomes a graph query — `graphify affected <pkg>
  --relation requires` — and the hubs (`god-nodes`) are the packages that cannot
  be removed whatever their rationale.
- **A trim phase** in `phases.toml`, after the last consumer of everything it
  removes and before the disk is frozen, idempotent and re-runnable from
  `image-trim.toml`. Rollback is the checkpoint that already exists
  (`build-orchestration` D3), not a new mechanism.
- **The gate is a rebuild, not a scan.** A verdict is accepted when the build
  still completes from the checkpoint and the image still boots to a multi-user
  OpenRC runlevel with the trim applied; a package that breaks either is
  reinstated and its verdict changed to `ships` with the failure recorded. The
  scan is evidence about ELF; the rebuild is evidence about everything else —
  the `.pc` file a later configure needs, the interpreter a script names, the
  binary a service calls by name.
- **Non-goals, stated where the claim is:** no size or boot-time figures before
  they are measured on this build; no binary stripping, which the book's own
  Stripping and Cleaning Up pages already specify and which this change cites
  rather than restates; no package manager; no removal of anything on the
  accelerator path.

## Capabilities

### New Capabilities

- `image-minimisation`: how a package earns a verdict, what evidence a verdict
  rests on, how the trim is applied and verified, and what the dependency graph
  is required to answer.

### Modified Capabilities

- `base-system`: it already requires that an excluded package be named with its
  reason and what breaks if it returns, but names no place that record lives, and
  the file it would naturally live in is derived and overwritten. The delta gives
  the record a home and a subset check against `base.lock`.

## Impact

- New: `image-trim.toml` (hand-authored, repository root, beside `class-map.toml`
  for the same reason), `scripts/build/` steps for the file map, the link scan,
  and the graph; one phase row in `phases.toml`.
- New, and already built during proposal: `graph/` inside this change — the
  declared-build graph generated from `base.lock` with `graphify`, its generator, and
  the shared-page table that changed this change's own design (D8). It carries no
  dependency edge that anything has measured, and says so.
- Evidence directory grows one file list per package — the same obligation
  `build-orchestration` D11 already imposes on every package, extended from
  "command output" to "files installed".
- `graphify` is a **build-host** tool (Python, `uv tool`), never an image package:
  nothing in this change may add it or its dependencies to `base.lock`. The graph
  it produces is a repository artifact, committed, so a reviewer can ask what a
  removal breaks without a built image.
- Task-level dependencies, not change-level: `build-orchestration` 4.x (phases,
  evidence, checkpoints) blocks the capture and the trim phase;
  `base-system-and-init` 3.1 owns the `base.lock` format this change reads but
  does not edit; `userspace-and-ml-stack` decides whether a compiler is `ships`
  or `build-only`, because a wheel with no matching sdist builds at install time.
- Nothing here needs the target machine. Every task is `(build)`: file and
  synthetic-fragment checks, `ldd` against built libraries, a phase run in the
  VM. What the trimmed image does on the target — boot time, memory freed, a
  training run unaffected — is a claim about hardware and is
  `target-hardware-bring-up`'s to make, with this change's phase table as its
  input.
