# 13. Triadж exit-crash (std::system_error в teardown) — musl-specific, обход `_exit`

**Дата:** 2026-11-15 · **Хост:** (build) `192.168.0.86`
**Следует за:** отчёт 12 (находка 2)

## Вопрос

После LOADER_OK, при нормальном завершении процесса: SIGABRT,
`std::system_error: No error information` (glcore/gpucomp; tls чистый).
Препотчеден (отчёт 12). Что это, и мешает ли это D3?

## Метод

Диагностические LD_PRELOAD-интерцепторы (musl, собираются в bwrap; исходники
`tools/diag/`) + контрольные прогоны:

1. **Потоки** — перехват `pthread_create/join/detach`: **ноль вызовов**.
   Паника не из thread-pool.
2. **Файлы** — перехват `open/openat/unlink/rmdir/access/mkdir`: **ноль
   ошибок** (и ноль вызовов teardown-характера). Паника не из file-cache.
3. **Контроль на glibc** — тот же **непатченный** glcore + glibc-джейл
   (ubuntu 24.04, bwrap, host-драйвер bound): `LOADER_OK`, **exit 0, без
   краха**. → Паника **musl-specific**, а не латентный NVIDIA-баг «везде».
4. **Момент** — harness, вызывающий `_exit(0)` сразу после dlopen:
   `LOADER_OK`, **exit 0, без краха**. → Бросок происходит в обработке
   нормального выхода (atexit / статические деструкторы), а не в dlopen.
   (Обёртка `exit()` через LD_PRELOAD не срабатывает: musl libc вызывает
   собственный `exit` напрямую, не через PLT — обход только через `_exit`
   в коде приложения.)

## Вывод

`No error information` = `std::error_code` по умолчанию (код 0, без
категории) → это **сознательный бросок голого `std::system_error()`** —
внутренняя паника NVIDIA-кода: какой-то инвариант в статическом teardown
не выполняется под musl (порядок/состояние деструкторов отличается от
glibc). Не вызов, упавший syscall'ом (тех бы были errno и код ошибки).

Глубина до корня (какой именно объект) требует gdb-сессии против
статически встроенного в glcore libstdc++ — отдельная задача, не блокер.

## Практика

- На загрузку, релокации и работу GL-кода крах **не влияет** (всё до exit).
- Тестовые harness'ы и CI: завершаться `_exit(code)` (не `exit`) — чистый
  exit 0, деструкторы NVIDIA не запускаются.
- Реальные процессы: exit-код 134 вместо 0 — косметика; результаты
  флешатся до teardown. Если когда-то станет блокирующим — gdb-триаж
  (зафиксировать адрес броска через `__cxa_throw` в статике glcore).

## Артефакты

- `tools/diag/fo.c` — интерцептор файловых операций (реusable).
- Интерцепторы потоков/exit — одноразовые, в `~/lite/glwork/` на (build).
